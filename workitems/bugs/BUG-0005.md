名称：内部快照拉取端点出站体再序列化致下游不可重算 snapshotHash
所属模块：管理系统（Java）
相关功能：FEAT-0008
测试用例：TC-0026
关联任务：TASK-0080
优先级：P1
问题现象：GET /internal/v1/config/snapshot（TASK-0026 交付）出站快照体经 Jackson 再序列化——数字形态被改写（如 5.000000→5.0），下游（TASK-0027 实证）从收到的体重算 SHA-256 与响应 snapshotHash（=原始存储字节哈希）恒不一致，「拉快照比对哈希」兜底（REQ-0013/REQ-0033 验收 2）被削弱为只能信任服务端字段。
预期行为：下游按 REQ-0013 契约「拉快照比对哈希」——收到的快照体应与其 snapshotHash 字段可互相验证（重算一致）。
实际行为：出站体为再序列化形态，重算哈希必然不同；Go 侧已退化为「对账锚点口径」（字段比对+形态校验+同版本漂移探测），原始完整性验证能力缺失。
复现步骤：1. backend dev 起（8098）；2. REST 拉 /internal/v1/config/snapshot（任一已发布 scope）得 snapshotHash 与快照体；3. 对收到的快照体（JSON 规范化后）算 SHA-256 → 与 snapshotHash 不一致；4. 对存储文件原始字节算 SHA-256 → 与 snapshotHash 一致（证哈希源为原始字节、出站体被改写）。
严重程度：一般
根因分析：TASK-0026 出站组装将存储文件解析为 JsonNode 后随响应 POJO 再序列化（Jackson 3），未透传原始字节——0024 的确定性序列化产物（哈希可验的前提）在出站链路丢失。
修复方案：出站快照体改为原始存储字节透传（Jackson 3 RawValue/原样内嵌，响应其余字段不变）；配可重算断言测试（响应体重算 SHA-256 == snapshotHash）+ 0026 既有测试回归。修复以微改 TASK-0080 承载（与 TASK-0079 合批派发）。
