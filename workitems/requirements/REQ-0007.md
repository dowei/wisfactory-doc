名称：设备状态判定（规则配置、引擎判定与展示链）
所属模块：跨系统（配置归管理系统、判定归计算引擎、展示归数据服务）
目标角色：实施/配置人员（配置）；全部展示端用户与对外 API 消费方（读取）
优先级：P0
业务目标：设备运行/停机/待机/故障状态不靠前端按数值现算，按模板配置规则由计算引擎统一判定，判定口径全厂一致（ADR-0004 三段式收口，任务包 T17）。
业务能力：配置段——模板上维护规则集（iot_status_rule：优先级、条件表达式〔Aviator、相对引用〕、状态编码/名称/颜色），保存时表达式语法与相对引用存在性校验，随配置发布下发；判定段——实例任一被引用数据项更新时触发，按 priority 升序逐条求值、首个命中即当前状态，全部不命中为 UNKNOWN 并打质量标记不硬套；当前状态写 Redis（iot:st:{tenant}:{instance}，JSON 含 statusCode/statusName/color/ts）；变化留痕——状态变化以约定数据项 STATUS 写 st_item_value（value=状态序号、quality=0、未变不重写）；展示段——展示端与对外接口经数据服务读 Redis 当前状态+st_item_value 历史，翻译以规则表与字典为准。
核心规则：【TD-0013 未决】状态序号稳定性——序号若按字典现算派生，增删状态编码将使历史 st_item_value 序号漂移，状态时长还原会错；需稳定状态编码字典（只增不删、禁用不复用序号）或按规则表固化序号。【TD-0014 未决】状态点位直绑路径（产品 §10.3「直绑优先」、枚举映射在模板上配置）在详细设计 §1.5B 无映射配置与直绑进 Redis 链路定义，需补落点或一期降级为仅规则判定。
非目标：展示端不做任何状态判定逻辑；不做状态告警（三期）；不做跨模板全局规则复用；不做实例级绕过模板自定规则结构。
验收标准：1. 同一设备在详情页状态区、车间页色块、对外 API 三处读取的当前状态一致；2. 构造「有电流且转速>0」判为运行，叠加故障条件命中时故障优先于运行；3. 无状态点位且规则全不命中展示 UNKNOWN 带质量标记，不显示为任一已知状态；4. 修改模板规则并发布后展示端翻译随之变化；5. 状态变化在 st_item_value 留痕且未变不重复写。
原始来源：状态点位直绑（优先）——数据项 RUN_STATE 直绑该点位，枚举映射在模板上配置；规则判定——无状态点位时用规则推导……规则在模板上配置、多条件带优先级（故障优先于运行）。／全部不命中时状态为 UNKNOWN 并打质量标记，不硬套默认状态。
