编号：ADR-0002
名称：TDengine 子表标签保留租户 ID 双保险
状态：已接受
创建时间：2026-11-21 03:05:54
创建者：coordinator
日期：2026-11-21
背景：产品设计 V2.1 §10A 要求子表标签再带租户 ID，作为「双保险与跨库排查」手段；详细设计 V1.0 §2.2 四张超级表（st_point_num、st_point_state、st_item_value、st_metric_value）标签均未含 tenant_id，租户隔离只靠每租户一库。两份定版文档冲突。
候选方案：A 不带 tenant_id，隔离只靠分库（详细设计现文）；B 四张超级表标签统一补 tenant_id（产品口径）；C 标签补 tenant_id 且同时建立标签租户与库租户的一致性巡检。
决定：B——四张超级表标签统一补 tenant_id；详细设计 §2.2 与附录 B 待上游修订；标签租户与库租户的一致性比对纳入运维巡检内容（巡检实现为后续任务）。
理由：标签在 TDengine 里是子表级元数据，一张子表只存一份，没有逐行成本，这是它便宜的原因。它买到的不是「防写错」——防写错靠接入服务从令牌解析租户、选库写入，详细设计已有这一步——而是可审计与可追溯：定期扫一遍标签租户与库租户不一致的子表，写错能发现；数据一旦离开库上下文（导出、备份恢复到别的集群、推给中台落库），库名上下文就丢了，标签让数据自带出身。成本接近零，收益是实打实的排查能力。方案 A 被放弃因省下的成本趋零而丢失审计能力。
影响范围与副作用：详细设计 §2.2 与附录 B DDL 修订（四张超级表 TAGS 各加 tenant_id BIGINT）；运维巡检任务包增加「标签租户与库租户一致性比对」巡检项；数据服务查询条件不变（分库已隔离，tenant 标签不参与过滤）。
关联对象：无既有对象；后续 FEAT（接入落库、计算引擎写入）与运维巡检 TASK 引用本 ADR。
