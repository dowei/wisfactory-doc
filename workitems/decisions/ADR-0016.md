名称：数据权限翻译组件实现口径定版（七项裁决）
日期：2026-11-21
背景：TASK-0005（六步翻译组件）动工前的口径清点（素材见 reports/TASK-0005-inputs.md 开放点 1-10）发现七处详细设计未成文的实现口径：①子树展开上限（FEAT-0002 明文要求 ADR 留痕）；②空结果与 403 的接口级判定规则；③仅本人（TD-0044）「配置类对象」的适用集；④多角色并集时 scope=4 的合并语义；⑤中台 scope JSON 结构（§1.10 只有「含子树标记」一句话）；⑥点位双条件 OR 对 NULL（未绑部门）的归类（TD-0043 fail-closed 的 SQL 落点）；⑦TDengine 下推标签名（§4.1 写 instance_code/dept，§2.2 实际为 instance_key/dept_id）。开放点 6（sys_role 系租户隔离二选一）已由 TASK-0002 按「直接加字段」实现消解；开放点 5（缓存失效粒度）归 TASK-0006；开放点 10（dept_id 必填校验位置）归 TASK-0012 服务层。
候选方案：逐项均有维持缺省建议 / 改判 / 搁置三向；本批七项全部采缺省建议并成文（原状为各文档只言片语，不成文则六步实现必走样）。
决定：逐项定版——
1. 子树展开上限：配置项 `ot.dataperm.subtree-max`（默认 5000 实例）；超限**截断并 WARN**（不报错不降级——权限组件故障不得阻断业务查询，截断按 ancestors 路径序保近端实例）；WARN 日志格式 `[DATAPERM] subtree truncated user=<id> kept=<n> cap=<n>`。落点：TASK-0005 步骤 4。
2. 空结果 vs 403 判定规则：按接口形态判定而非逐个枚举——GET 集合类（/list、/tree、/history、/curve、/realtime 等集合语义）返回空集；GET 单对象类（/{id}、/{code} 详情）返回 403。组件提供两种策略常量（SCOPE_EMPTY / SCOPE_FORBIDDEN），接口实现按形态选用；未来新增接口自动归类，无需维护清单。落点：TASK-0005 组件 + TASK-0007 红线用例。
3. 仅本人（TD-0044）适用集：「配置类对象」= iot_ 配置表的管理面列表查询（字典/模板/实例/点位/网关/通道/指标等）；scope=4 时这些列表按 create_by=当前用户过滤；时序/指标/曲线查询按空集；框架 system 系列表沿用框架 DataScopeService 既有语义。落点：TASK-0005 步骤 2/5。
4. 多角色并集与 scope=4 合并：部门集合仅由 scope∈{1,2,3,5} 的角色并集产出；任一角色 scope=4 不并入部门集合，而是给最终查询条件追加 `OR create_by=当前用户` 分支（仅配置类）；时序类查询 scope=4 不贡献任何可见性。即：最终条件 = (instance_id ∈ 并集) OR (create_by=me，仅配置类且存在 scope=4 角色)。落点：TASK-0005 步骤 1/5。
5. 中台 scope JSON 结构：`{"instanceIds":[...], "subtree":true}`——instanceIds 为实例 id 数组；subtree=true 时数组内实例按步骤 4 子树展开，false 精确匹配；scope 为 null 或空数组 = 无任何数据权限（默认拒绝，与 §1.10「为空表示无任何数据权限」一致）。中台查询复用步骤 3-5：scope 展开成可见实例集合后与登录用户走完全相同的拼装与下推。落点：TASK-0005 组件解析器 + TASK-0051 开通界面。
6. 点位双条件 NULL 归类：查询条件 `(dept_id IN 部门集 OR bound_instance_id ∈ 可见集)` 结构性满足 TD-0043——scope=1（全部）不做过滤（未绑部门行对租户管理员可见）；其余 scope 下 NULL 行两条件皆不命中=不可见（fail-closed）。不做特判、不写 OR dept_id IS NULL。落点：TASK-0005 步骤 5。
7. TDengine 下推标签名：以超级表契约 v1.0.0（resources/contract/tdengine-super-tables.md）实际标签为准——instance_key、dept_id；详细设计 §4.1 的「instance_code/dept」为行文旧称，组件下推条件一律用契约标签名。落点：TASK-0005 步骤 5（差异已留痕本条）。
理由：七项均为「同一组件同一口径」原则下的必要定版——不成文则管理面与数据服务两处实现必然分叉；各项缺省建议均取最小实现与 fail-closed 方向（截断不阻断、默认拒绝、NULL 不放行），与 REQ-0002 的安全默认基调一致。方案改判项无：无证据支持偏离缺省。
影响范围与副作用：TASK-0005 按本 ADR 实现（brief 直接引用）；TASK-0006 缓存与失效（开放点 5）沿用本 ADR 的组件边界；TASK-0007 红线用例按第 2 条判定规则构造；TASK-0012 按第 7 条之外的 dept_id 服务层校验口径实现；TASK-0051 的 scope JSON 按第 5 条；超级表契约标签名不受影响（§4.1 行文旧称随 PDF 下游修订对齐，登记待上游修订清单）。
