编号：ADR-0001
名称：点位超级表按值类型分两张口径
状态：已接受
创建时间：2026-11-21 03:05:53
创建者：coordinator
日期：2026-11-21
背景：产品设计 V2.1 §9.1 定版口径为点位原始值按数据类型分 4 张超级表（瞬时量、累计量、状态量、开关量各一张，理由「字段类型不同，分表避免空列」）；详细设计 V1.0 §2.2 实际划分按值类型分 2 张（st_point_num 存 DOUBLE、st_point_state 存 INT，kind 标签区分 INSTANT/CUMUL/STATE/SWITCH）。两份定版文档冲突，动工前必须定口径。
候选方案：A 按产品 §9.1 分 4 张（数据类型各一张）；B 按详细设计分 2 张（值类型 DOUBLE/INT 各一张，kind 标签保留四类语义）；C 折中 3 张（瞬时、累计各一张，状态与开关合一张）。
决定：B——以详细设计为准：点位超级表 st_point_num、st_point_state 两张，四类语义由 kind 标签承载；产品 §9.1 待上游修订对齐。
理由：产品文档「字段类型不同、分表避免空列」的理由只在 DOUBLE 与 INT 之间成立——瞬时量与累计量同为 DOUBLE，拆成两张同构超级表物理上没有任何收益，只多一倍子表管理和查询路由；四类语义靠 kind 标签完整保留，查询口径不丢。超级表列类型固定是 TDengine 的实际约束，2 张分法正是按该约束设计。保险路径：将来状态量若不用 INT 枚举改存字符串，新增一张 st_point_text 即可，不影响已有两张，扩展路未堵死。方案 A 被放弃因同构分表无收益；方案 C 被放弃因多一张表的维护成本换不来类型收益。
影响范围与副作用：详细设计 §2.2 与附录 B 为实现依据；产品 §9.1 待上游修订（V2.2 或勘误）；TDengine 超级表契约（三份冻结契约之一）按「2 张 + kind 标签」落 FEAT；接入服务写入分发按 kind 判定；后续 TC 需覆盖四类 kind 的落表正确性。
关联对象：无既有对象（intake 前置决策）；后续 REQ（时序存储口径）、FEAT（接入落库）引用本 ADR。
